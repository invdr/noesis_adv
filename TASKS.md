# План работ — ГСК TOWER

Декомпозиция [PRD.md](./PRD.md) на **вехи** (milestones) и задачи. Каждая веха —
поставляемый кусок продукта: после вехи 1 есть вход в CRM, после вехи 2 — полный
цикл заявки, и т.д. Внутри вехи задачи сгруппированы по surface в порядке потока
`contracts → backend → webapp/website → infra`.

Поток для любого эндпоинта неизменен: **схема в `packages/contracts` → Zod-валидация
в route → auth/роль-guard → service → Prisma → DTO**. Любая задача с API начинается
с контракта.

**Текущий статус:** готовы Вехи 1–11: CRM-заявки, воронки, контакты, партнёры,
аналитика, калькулятор, контент лендинга, публикация сайта из CRM, деплой на VPS
и контур проверок. Документ остаётся источником декомпозиции и истории решений.

Легенда статусов: `[ ]` — не начато, `[~]` — частично есть, `[x]` — готово.

## Веха 1. Фундамент CRM

Вход, сессии, роли и динамическая воронка статусов — база, на которой стоит вся CRM.

### Аутентификация и роли
- [x] Контракты: `LoginRequest` (вход по email), `SessionUser` (id, email, роль,
  `mustChangePassword`), `ChangePasswordRequest`; роли `admin | manager`.
- [x] Модели `User` (email, хеш пароля, роль, статус, флаг смены пароля) и
  `Session` (хеш токена, `userId`, TTL, последняя активность); миграция через `prisma:migrate`.
- [x] Сервис auth: хеширование (argon2id, `Bun.password`), серверная сессия в
  `httpOnly`-cookie, скользящий TTL 12 ч с продлением при активности.
- [x] Роуты: `POST /api/auth/login`, `/logout`, `GET /api/auth/me`, `POST /api/auth/change-password`.
- [x] Guard'ы `requireAuth` / `requireRole('admin')`; прекращение сессий заблокированного юзера.
- [x] Seed первого администратора из `.env` (`db:seed`) с флагом смены пароля.
- [x] Webapp: экран логина, состояние сессии, редирект неавторизованных,
  обработка 401, принудительная смена пароля при `mustChangePassword`.

### Воронка статусов (этапы заявок)
- [x] Контракт `Stage` (id, `name`, `order`, `kind: in_progress | won | lost`,
  `isEntry`, `isArchived`) + `createStage`/`updateStage`/`reorderStages`/`archiveStage`;
  в `Lead` заменить enum-статус на `stageId`, удалить `leadStatusSchema`.
- [x] Модель `Stage` (не enum): `name`, `order`, `kind`, `isEntry`, `archivedAt?`;
  у `Lead` — `stageId` (FK) вместо `status`. Сидинг дефолтной воронки:
  Новая (вход) → В работе → Недозвон → Встреча/показ → Бронь → Сделка (won) → Отказ (lost).
  Миграция старых статусов: `new→Новая`, `in_progress→В работе`, `done→Сделка`, `rejected→Отказ`.
- [x] Инварианты (только по живым этапам, в сервисе — не в БД): ≥1 `won`, ≥1 `lost`,
  **ровно 1** `isEntry`; нельзя архивировать/сменить `kind`/снять `isEntry`, если
  это нарушит инвариант. Новая заявка падает в этап `isEntry`.
- [x] Признак «активна/закрыта» выводится из `kind` этапа заявки: `in_progress` —
  активна; `won`/`lost` — закрыта (уходит из активной работы, дата след. контакта не нужна).
  Потребляется в Вехе 2: при переходе в `won`/`lost` дата след. контакта снимается.
- [x] Роуты: `GET /api/stages` (все роли; `?includeArchived` — admin),
  `POST`/`PATCH`/`PATCH /reorder`/`DELETE` (admin). «Удаление» = архивация с
  обязательным `targetStageId`; перенос в терминальный (`won`/`lost`) этап — только
  после подтверждения (`confirmTerminal`). Переходы заявок между этапами свободные.
- [x] Webapp (admin): экран управления этапами — добавление, переименование,
  смена `kind`, флаг входа, перестановка порядка (↑/↓; drag — позже), архивация
  с переносом заявок и предупреждением о терминальном этапе.

> **Решения из обсуждения (продукт):** воронку настраивает только admin (менеджер
> двигает заявки по этапам). Этап входа — явный флаг (не «первый по порядку»).
> «Удаление» = архивация (история/аналитика сохраняются). `kind` можно менять
> после создания. Терминальные этапы живут в общем плоском порядке. Учётка `admin` —
> конфигуратор: в аналитику «по менеджерам» не входит и исполнителем по умолчанию
> не назначается (учесть в Вехах 2 и 5).

## Веха 2. Заявки end-to-end

Полный цикл: приём с 4 точек лендинга → защита и согласие ПДн → уведомления →
обработка в CRM.

### Приём заявок
- [x] Расширить контракт `Lead`: источник `hero_form | project | calculator | contacts`,
  привязка к ЖК, сообщение, согласие ПДн, honeypot; хелпер нормализации телефона
  `+7 (___) ___-__-__` → `+7XXXXXXXXXX`.
- [x] Расширить модель `Lead`: источник, `projectId?`, сообщение, флаг «повторная»,
  `assigneeId?`, `stageId`, дата следующего контакта.
- [x] Модели: согласие ПДн (признак, время, IP), `LeadNote` (автор, текст, время),
  `LeadStatusEvent` (этап, автор, время — история смен статуса).
- [x] Сервис приёма: создание с любой из 4 точек; honeypot (молча отклонять);
  анти-спам по паре «IP+телефон» (5/10мин) + потолок по IP (20/10мин — продуктовое
  решение вместо жёсткого 5/IP); детект повторной за 30 дней с авто-назначением
  менеджеру прошлой активной заявки; запись согласия ПДн; новая заявка — этап «Новая».
- [x] Telegram: сообщение в чат отдела продаж (имя, телефон, источник, ЖК, время,
  ссылка); токен/chat id из `.env`; сбой не ломает создание заявки.
- [x] Формы на лендинге: hero + калькулятор (`calculator`, параметры расчёта в
  сообщение) + контакты (`contacts`) через модалку в стиле лендинга; маска телефона,
  чекбокс согласия, honeypot; состояния успеха/ошибки без изменения дизайна.
  Карточка ЖК (`project`) — в Вехе 3 (вместе с моделью ЖК); ссылка на политику у
  согласия — в Вехе 4 (когда появится страница политики ПДн).

### Обработка в CRM
- [x] Контракты списка (фильтры, пагинация) и карточки; guard видимости в сервисе:
  менеджер — свои + неназначенные, admin — все, связанные по телефону — read-only.
- [x] `GET /api/leads`: фильтры (статус, источник, ЖК, ответственный, период, поиск
  по имени/телефону), пагинация 25/стр, сорт от новых; экспорт CSV (UTF-8+BOM, `,`).
- [x] Карточка: смена статуса (→ `LeadStatusEvent`), назначение ответственного
  вручную (менеджер — себе/в очередь, адресно — admin*), заметки (CRUD; свои —
  автор, любые — admin), дата следующего контакта, связанные заявки, история смен статуса.
- [x] Webapp: UI списка (фильтры, поиск, пагинация, метка «повторная», экспорт) и
  карточки со всеми блоками. *Адресное назначение admin'ом на конкретного
  менеджера реализовано в Вехе 5 (список менеджеров в карточке заявки).

## Веха 3. Контент и файлы

Хранилище файлов и три типа контента, управляемые из CRM.

### Хранение файлов

> Продуктовые решения и устройство — в [docs/files-storage.md](./docs/files-storage.md).
> Ключевое: файлы грузятся вместе с сохранением сущности (не «залил → ссылка →
> приклеил»), поэтому загрузка — переиспользуемый сервис, вызываемый из эндпоинтов
> ЖК/новостей/документов; обработка изображений синхронна. Клиентская подсветка
> негодных файлов и формы — вместе с экранами ЖК/новостей (задачи ниже).

- [x] Бэкенд загрузки: приём multipart, сохранение в каталог на томе VPS, валидация
  типа по magic bytes + размеру (изображения jpeg/png/webp ≤10 МБ; документы
  pdf/офис ≤25 МБ), обезличенные имена + метаданные, возврат публичной ссылки.
- [x] Обработка изображений: несколько размеров + превью + WebP для фото ЖК и
  обложек новостей (оригинал сохраняется; документы — без преобразования);
  метаданные для `srcset`.
- [x] Инфра: каталог вне git на постоянном томе, раздача через nginx.

### Жилые комплексы (ЖК)

> Продуктовые решения и устройство — в [docs/projects.md](./docs/projects.md).
> Застройщик заведён отдельной сущностью-справочником (ведёт admin), а не
> свободным текстом.

- [x] Контракт `Project` (название, адрес, цена «от», комнатность, застройщик,
  обложка, галерея, описание, статус публикации, «Скоро на сайте», бейджи
  текст+цвет, slug) + контракт `Developer` и модели со связями.
- [x] Сервис/роуты: CRUD (manager+admin), стабильный slug (заморожен),
  блокировка по версии, архив/восстановление, публичный `GET` — только
  опубликованные; загрузка фото через сервис файлов. Справочник застройщиков
  (`/api/developers`, ведение — admin).
- [x] Webapp: список ЖК (фильтры, архив) и форма редактирования (данные, фото с
  обложкой/порядком, описание, публикация/«скоро», бейджи) + справочник
  застройщиков. *Документы по ЖК — отдельной задачей ниже.*

### Новости и акции

> **Решения из обсуждения (продукт):** метка/категория — управляемый
> справочник (ведёт admin; новость ссылается на метку по id — переименование
> подхватывается, удалить используемую метку нельзя, только архив), а не
> свободный текст: на лендинге метки в едином стиле, цвет не нужен. Текст
> статьи — простые абзацы (1:1 с дизайном, без rich-text и картинок внутри).
> Помимо полного текста — отдельное «краткое описание» для карточки каталога
> (так в макете). Дата редактируемая (по умолчанию сегодня), показ управляется
> статусом, без отложенной публикации. slug заморожен (как у ЖК); «удаление» =
> архивация; обложка обязательна для публикации.

- [x] Контракт `NewsLabel` (id, name, slug, order, архив) + `upsert`/архив и
  модель-справочник меток.
- [x] Контракт `News` (заголовок, slug, метка `labelId`, дата, обложка, краткое
  описание, текст, статус) + `upsertNewsSchema` с обязательностью по статусу
  (черновик — заголовок; публикация — заголовок+метка+дата+обложка+текст) и модель.
- [x] Сервис/роуты меток (admin): CRUD, архив/восстановление, защита от удаления
  используемой.
- [x] Сервис/роуты новостей: CRUD (manager+admin; обложка через файловый сервис),
  slug заморожен, блокировка по версии, архив/восстановление; публичный `GET` —
  только опубликованные, от новых к старым, + статья по slug.
- [x] Webapp: список и редактор новости + ведение справочника меток (admin).

### Документы по ЖК

> **Решения из обсуждения (продукт):** категории — **общий справочник** (ведёт
> admin, задаёт порядок), а не «произвольные внутри ЖК»: на главной навигация
> идёт от категории к ЖК (нужна общая ось категорий) — **сознательное отклонение
> от ПРД §«Документы по ЖК»** в пользу неизменяемого дизайна лендинга. Документ
> бывает двух видов — **загруженный файл** (PDF/офис ≤25 МБ; мелкая строка
> карточки = тип·размер) или **внешняя ссылка** (`url` + ручная подпись; открытие
> в новой вкладке, только `http(s)`). Загрузка/удаление документа — мгновенная
> отдельная операция в карточке ЖК (не в снимке «Сохранить ЖК»); удаление файла —
> сразу и навсегда. Название — обязательное; порядок — по добавлению. Пустые
> категории на главной скрыты; в категории показываются только ЖК с такими документами.

- [x] Контракт `DocumentCategory` (id, name, slug, order, архив) + `upsert`/архив
  и модель-справочник категорий (общий, не привязан к ЖК).
- [x] Контракт `Document` (имя, `categoryId`, вид `file | link`: для файла —
  `Asset`/тип/размер, для ссылки — `url` + подпись) и модель к `Project`.
- [x] Сервис/роуты категорий (admin): CRUD, архив, защита от удаления используемой.
- [x] Сервис/роуты документов: добавление (файл через файловый сервис или ссылка)
  и удаление в карточке ЖК (manager+admin); жёсткое удаление ЖК сносит и файлы
  документов; публичный `GET` по ЖК, сгруппированный по категориям, + глобальная
  карта «категория → ЖК» для блока на главной.
- [x] Webapp: управление документами внутри карточки ЖК + ведение справочника
  категорий (admin).

## Веха 4. Публичный лендинг

Лендинг на данных из API, редактируемая «обвязка», публикация, SEO, ПДн и cookies.
Дизайн и вёрстка неизменны.

> **Детальный план и согласованные продуктовые решения — в
> [docs/VEHA4_PLAN.md](./docs/VEHA4_PLAN.md).** Реализуется фазами:
> **4.1** — лендинг на реальных данных (сид 1:1 со статики, страницы `/zhk/<slug>`
> и `/news/<slug>`, ПДн + cookie-баннер, SEO; публикация на этом шаге была ручной);
> **4.2** — очередь публикации (ручной запуск из CRM, дебаунс, Telegram-алерт);
> **4.3** — редактируемая «обвязка» сайта из CRM + Яндекс.Метрика (опционально).
> Ключевые решения: SSG; реальные URL + наложения остаются; снятый ЖК → редирект
> на каталог; пустые блоки скрываются; фото переносятся со старого облака в наше
> хранилище сидом на VPS.

### Лендинг на данных из API
- [x] **(4.1)** Каталог ЖК на главной из API; страницы ЖК `/zhk/<slug>` (`srcset`,
  документы); блок «Акции и новости» + страница «Все акции и новости» + статья
  `/news/<slug>`; подтягивание контента из API на этапе билда (SSG static);
  наложения остаются (карточки получают `href`, JS перехватывает клик); пустые
  блоки и их пункты меню скрываются; снятый ЖК/новость → 301 на каталог (nginx).
- [x] **(4.1)** Сид 1:1 со статики (3 застройщика, 8 ЖК, 6 новостей, 4 категории
  документов; фото переносятся со старого облака в наше хранилище, дедуп по URL).
- [x] **(4.1)** SEO: уникальные title/description, canonical, Open Graph/Twitter,
  `sitemap.xml` + `robots.txt`, Schema.org Organization.

### Управление контентом сайта (admin)
- [x] **(4.3)** Модель/контракт настроек: видимость и порядок ЖК на главной; подписи и
  ссылки кнопок/секций/навигации; параметры блока новостей; контакты и реквизиты
  (Telegram chat id — через `.env`). Сервис/роуты (admin) + UI. Реализация:
  singleton `SiteSettings` (JSON-переопределения поверх дефолтов в коде),
  `backend/src/site-settings/` (admin-only, блокировка по `expectedUpdatedAt`),
  гайдрейлы длины + валидация ссылок в `packages/contracts/src/site-settings.ts`,
  правка ставит флажок неопубликованных изменений (middleware), экран «Сайт» в CRM (admin).
- [x] **(4.3)** Лендинг использует настройки на этапе билда вместо хардкода
  (`fetchSiteSettings` + `buildChrome`; навигация, контакты, подписи, второй
  контакт, порядок/скрытие ЖК, число новостей; бегущая строка — те же видимые ЖК,
  что и каталог). «Скрыть ЖК» убирает из каталога, блока «Документы» и бегущей
  строки, но `/zhk/<slug>` и sitemap остаются.

### Очередь публикации
- [x] **(4.2)** Очередь публикации; бэкенд помечает сохранённые правки как
  неопубликованные, админ отдельно ставит их в публикацию; дебаунс ~2 мин,
  сериализация (≤1 сборки одновременно). Реализация: модель `SiteBuild` +
  сервис (`backend/src/site-build/`), middleware-сигнал на контентных роутах,
  внутренние ручки claim/result для хост-сборщика (`infra/site-builder.sh` +
  `gsk-site-builder.service`), атомарный релиз+симлинк (`infra/build-website.sh`,
  nginx раздаёт `current`), сайт на последней рабочей версии при сбое +
  Telegram-алерт, сторожок простоя, индикатор статуса в CRM, сид «бутстрап-онли».

### Соответствие 152-ФЗ и cookies
- [x] **(4.1)** Публичная статичная страница политики ПДн (`/privacy`); ссылка
  рядом с чекбоксом согласия во всех формах.
- [x] **(4.1)** Баннер cookies при первом визите (ссылка на политику, согласие в
  localStorage, в стиле лендинга, не перекрывает контент).

### Веб-аналитика (Яндекс.Метрика)
- [x] **(4.3)** ID счётчика как настройка (CRM, admin), на всех публичных страницах
  (сниппет в `SiteHead`, анонимизация — без Вебвизора; пусто = не грузим). Упоминание
  Метрики добавлено в текст Политики ПДн (`/privacy`).
- [x] **(4.3)** Цель «отправлена заявка» с параметром-источником (`ymGoal('lead',{source})`);
  открытие страницы ЖК (`zhk_view` — наложение и реальная страница) и клик по телефону
  (`phone_click`, делегировано на всех страницах).

### SEO
- [x] Уникальные `title`/`description` (для ЖК и новостей — из контента); ЧПУ по
  стабильному slug; Open Graph / Twitter Card; `sitemap.xml` (с `lastmod` у
  новостей) + `robots.txt`; `canonical` + Schema.org (Organization на главной,
  `NewsArticle` на статьях). *Индексация завязана на домен (`INDEXABLE` от
  `SITE_URL`): пока выдача по голому IP — `robots` закрыт, при появлении домена
  открывается сам.*

## Веха 5. Аналитика и пользователи

Админские разделы: дашборд заявок и управление учётками.

## Веха 7. Калькулятор рассрочки в CRM

Перенос менеджерского модуля расчёта рассрочки в CRM: настраиваемые ЖК/цены
(admin), сам калькулятор (все роли) и сохранение расчёта в заявку. Шире исходного
ТЗ: в PRD «калькулятор рассрочки» — только точка приёма заявки на лендинге
(источник `calculator`, Веха 2); здесь это отдельный внутренний инструмент.

### Контракты (движок и API)
- [x] Схема конфига (`calculator.ts`): ЖК → типы → матрица цен по осям
  `[бракет срока][подтип|default][этаж]`. Модель цен — «базовая (cash) ₽/м² +
  надбавка за рассрочку» (надбавка на вариант оплаты: Δ₽/м² или %); варианты
  оплаты хранят долю ПВ (`downFraction`) и флаг базового; видовая надбавка;
  маткапитал с правилом допуска в конфиге (полная оплата / любая рассрочка /
  список месяцев). Глобалки (singleton): суммы маткапитала + режим округления.
- [x] Чистый движок `computeInstallment` (единый источник математики для форм
  настроек и расчёта): две модели — «после наценки» (A) и «до наценки» (B, наценка
  только на финансируемый остаток); режимы округления платежа (в т.ч. подгонка
  последнего месяца и округление до шага); скидки (₽ / % / СВО-процент от остатка);
  произвольный ПВ (₽/%); обязательный платёж при «без взноса»; допуск маткапитала
  и его положение до/после наценки в модели B. Фолбэк на модель A, если нет базовой
  цены. Покрыт юнит-тестами (`packages/contracts/test/calculator.test.ts`).
- [x] API-контракты (`calculator-api.ts`): DTO ЖК с полным конфигом; upsert/reorder/
  archive с оптимистичной блокировкой (`expectedUpdatedAt` → 409, как у ЖК/новостей/
  настроек); глобальные настройки; снимок расчёта (контекст + ввод + результат
  «как есть» passthrough + подписи, опциональная привязка к заявке `leadId`).

### Бэкенд (`backend/src/calculator/`)

- [x] Сервис: валидация конфига движковой схемой на входе, оптимистичная блокировка,
  архивация/восстановление; DTO Prisma → контракт.
- [x] Идемпотентный сид: 9 ЖК из исходного `config.js` в формате «база+надбавки»

### Webapp
- [x] Экран калькулятора (`CalculatorView`, все роли) и админ-настройки цен/ЖК/

> зелёным; прод не трогаем (деплой вручную по SSH, отдельно).
