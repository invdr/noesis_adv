# Анализ: tower-site как основа CRM + сайт для РА «Noesis» (сити-форматы, Грозный)

> Оценка пригодности репозитория [`invdr/tower-site`](https://github.com/invdr/tower-site)
> как базы для рекламного агентства, продающего размещение на сити-форматах в Грозном.
> Дата: 2026-07-08.

## Резюме (вердикт)

**Переделать реально, база сильная — рекомендую брать.** Порядка **60–70% кода
переносится почти без изменений** (весь «водопровод» CRM, приём заявок, контакты,
аналитика, хранение файлов, новости, конвейер публикации сайта, деплой, CI).
Оставшиеся **30–40%** — это доменная переделка: каталог ЖК → каталог рекламных
конструкций и **принципиально новый блок «инвентарь + бронирование по периодам»**,
которого в исходнике нет вовсе. Плюс визуальный редизайн лендинга и карта города.

Ключевое совпадение: тот же правовой и инфраструктурный контекст (152-ФЗ,
русскоязычный UI, VPS, Telegram-уведомления) и та же архитектурная задача —
**публичный сайт на данных из CRM + сама CRM + приём лидов**. Мы не воюем с
фреймворком: недостающее — аддитивное, а не противоречащее заложенной архитектуре.

Главный технический риск — не «переделать существующее», а **спроектировать и
построить новое**: занятость конструкции во времени (свободна ли поверхность №123
в сентябре) и гео-карта. В исходнике ресурс во времени не бронируется —
лиды и этапы воронки этого не покрывают.

---

## Что такое tower-site

Зрелое, аккуратно написанное монорепо (Bun workspaces) строительной компании
«ГСК TOWER»: публичный лендинг + мини-CRM для обработки заявок. Готовы Вехи 1–11.

| Surface | Стек | Назначение |
| --- | --- | --- |
| `website/` | Astro (SSG) | Публичный лендинг, SEO, данные из CRM на этапе сборки |
| `webapp/` | React 19 + Vite (CSR) | CRM за логином |
| `backend/` | Hono + Prisma + PostgreSQL 18 | API |
| `packages/contracts/` | Zod + TypeScript | Единый источник схем/DTO для фронта и бэка |
| `infra/` | Docker Compose + nginx | Деплой на VPS |
| `mobile/` | Expo (заготовка) | На будущее |

**Объём:** ~35 тыс. строк TS/TSX/Astro (backend ~9.3k, webapp ~11.4k,
contracts ~3.2k, website ~1.8k).

**Оценка качества — высокое.** Признаки зрелости:
- Бэкенд нарезан по фиче, а не по слою: `route → Zod-валидация → auth-guard →
  service → Prisma → DTO`. Единый поток, легко расширять новыми сущностями.
- **Контракты-первыми**: новый эндпоинт начинается со схемы в `packages/contracts`,
  её же переиспользуют формы фронта и API-клиент. Меньше рассинхрона.
- Продуманные инварианты: «удаление = архивация» почти везде (ссылки на историю
  целы), учёт согласия ПДн (время + IP), инварианты воронок в сервисе, дедуп
  контактов по телефону, анти-спам и троттлинг лидов.
- Есть тесты (contracts + backend + webapp) и E2E-смоук на Playwright, CI на
  GitHub Actions (typecheck + тесты).
- Отдельный конвейер публикации: правки в CRM помечаются черновыми, кнопка
  «Опубликовать» ставит пересборку статического сайта в очередь и атомарно
  переключает релиз.
- Русскоязычный домен и комментарии, 152-ФЗ уже заложен.

## Карта переноса

### ✅ Берём почти как есть (домен-независимое ядро, ~60–70%)

| Блок | Модели / модули | Комментарий |
| --- | --- | --- |
| Аутентификация, роли, сессии, пользователи | `User`, `Session`, `auth/`, `users/` | admin/manager — подходит 1:1. Восстановление доступа, смена пароля. |
| Ядро CRM: воронки и этапы | `Funnel`, `Stage`, `stages/`, `funnels/` | Универсальная воронка продаж, домен-независима. Только терминология. |
| Лиды и обработка | `Lead`, `LeadNote`, `Lead*Event`, `leads/` | Приём с сайта, ручной приём, назначение, «следующий контакт», журналы. Всё нужно РА как есть. |
| Приём заявок с сайта | формы лендинга + `lead-throttle`, `rate-limit` | Анти-спам, троттлинг, 152-ФЗ согласие (время+IP) — переносится 100%. |
| Контакты и партнёры | `Contact`, `ContactType`, `contacts/` | client/realtor/agency. Для РА: рекламодатель + агентство/посредник. Ложится почти дословно. |
| «Мой день» / повестка | `AgendaView`, `nextContactAt` | Задачи менеджера по времени — нужны РА без изменений. |
| Аналитика | `analytics/`, `partner-analytics/` | Конверсия по воронке/источнику/партнёру. ~90% переносится, добавим срезы по конструкциям/выручке. |
| Хранение файлов | `Asset`, `files/` | Картинки с WebP-рендишенами под `srcset`, документы. 100%. |
| Новости / акции | `News`, `NewsLabel`, `news/` | У РА тоже есть блок новостей/кейсов. 100%. |
| Публикация сайта | `SiteBuild`, `SiteSettings`, `site-build/`, `site-settings/` | Конвейер «черновик → опубликовать → пересборка» переносится архитектурно 1:1. |
| SEO, cookies, политика ПДн | `robots`, `sitemap`, `CookieBanner`, `privacy` | 100%. |
| Инфраструктура | `infra/`, `docker-compose`, nginx, CI | VPS + nginx + бэкапы + деплой. Меняются только имена/домен. |
| Документы по сущности | `DocumentCategory`, `Document` | Паттерн переиспользуется: прайсы, презентации, ГОСТ/паспорта конструкций. |

### 🔧 Переделываем (доменный каталог)

| Было (недвижимость) | Станет (наружная реклама) | Объём |
| --- | --- | --- |
| `Project` (ЖК): `priceFrom`, `rooms`, `slug`, галерея | **`Surface`/`Конструкция`** (сити-формат): адрес, **гео-координаты**, формат/габариты (1.2×1.8), сторона A/B, подсветка, тип потока/GRP, фото/макет, цена за период | Средний — модель меняется по полям, но паттерн (карточка каталога + страница) сохраняется |
| `ProjectImage` | Фото конструкции / фотомонтаж макета | Переиспользуем паттерн |
| `Developer` (застройщик) с реквизитами | **Владелец сети / оператор** конструкций **или** убрать; реквизиты юрлица переносим на договоры | Малый |
| `ProgressAlbum`/`ProgressPhoto` (ход стройки помесячно) | **Фотоотчёты о размещении** помесячно по конструкции | Малый — паттерн «альбом за месяц по объекту» ложится идеально |
| `DocumentCategory`/`Document` (по ЖК) | Прайс-лист, презентация, паспорт конструкции, ГРП-данные | Малый |

### ❌ Выкидываем или переосмысляем

| Блок | Судьба |
| --- | --- |
| `CalcComplex`, `CalculatorSettings`, `CalcSnapshot` (калькулятор рассрочки) | Логика рассрочки застройщика неприменима. Либо **удалить**, либо **переписать** в калькулятор стоимости кампании (N конструкций × M периодов × цена ± сезонный коэффициент) — это другая логика. |
| `ProjectLayout` (планировки квартир) | Не нужно; при желании — «монтажный лист / техпаспорт» конструкции. |
| Поле `rooms` (комнатность) и калькулятор на лендинге | Убрать / заменить блоками наружной рекламы. |

### 🆕 Чего НЕТ и что нужно построить с нуля (главная работа)

Проверено поиском по коду: **нет** ни гео-координат, ни карты, ни бронирования
ресурса по периодам, ни календаря занятости. Для наружки это ядро продаж.

1. **Инвентарь и бронирование во времени** — центральная новая сущность.
   `Booking`/`Размещение`: конструкция × рекламодатель × период (месяц / 2 недели /
   сезон) × цена × статус (бронь → подтверждено → в эфире → завершено). Именно она
   отвечает на вопрос «свободна ли поверхность №123 в сентябре». В tower-site
   ресурс во времени не бронируется — это новый бэкенд + новые контракты.
2. **Сетка занятости / загрузка** — представление «конструкции × месяцы» со
   статусами свободно/бронь/занято. Операционное сердце OOH-продаж, полностью новый UI.
3. **Карта города** — сити-форматы гео-привязаны; покупатель хочет карту Грозного
   с пинами и фильтрами. Компонента карты в исходнике нет. Логично взять
   Яндекс.Карты (уже используется Яндекс.Метрика — тот же вендор, тот же регион).
4. **Договоры / счета / акты / фотоотчёты как объект сделки** — у OOH выигранный
   лид превращается в договор с закрывающими документами. Частично моделируется
   как «won-лид + Booking + документы», но объект сделки, вероятно, стоит завести явно.

## Оценка объёма и рисков

**Что делает переделку реалистичной:**
- Тот же контур страны и права (152-ФЗ, русский UI, VPS, Telegram) — ничего не
  выкидываем из-за смены юрисдикции.
- Ядро CRM домен-независимо и зрелое — экономит месяцы.
- Недостающее (инвентарь, карта) — **аддитивно**: добавляем сущности в ту же
  архитектуру `contracts → service → dto`, а не переписываем каркас.
- Конвейер «данные из CRM → статический сайт → публикация» ровно тот, что нужен
  рекламному сайту-каталогу.

**Риски и на что заложить время:**
- **Бронирование во времени** — самый большой новый кусок. Нужны аккуратные
  инварианты (пересечение периодов, двойная бронь, опции/резервы с TTL). Это не
  переделка, а проектирование новой модели. Основной источник трудозатрат.
- **Редизайн лендинга.** В CLAUDE.md прямо сказано: лендинг — перенос готового
  дизайна 1:1, «визуальные стили не меняем без явной просьбы». Под наружку нужен
  новый дизайн (карта, каталог конструкций, форматы, охваты) — это отдельная работа.
- **Калькулятор.** Решить: удалить или переписать под смету кампании. Он завязан
  на несколько моделей и разделов CRM — «просто оставить» не выйдет, он про рассрочку.
- **Деплой.** Автодеплоя нет, прод обновляется вручную по SSH на VPS. Для нового
  проекта поднимаем свой сервер/домен и секреты — по накатанному, но заново.

**Грубая раскладка усилий** (порядок, не в часах):
- Ребрендинг + терминология + чистка недвижимости-специфики: небольшой.
- `Project → Surface` с гео/форматами/ценой за период: средний.
- **Инвентарь + бронирование + сетка занятости: большой (главный).**
- Карта на лендинге и в CRM: средний.
- Редизайн лендинга под наружку: средний–большой.
- Калькулятор (удалить/переписать): небольшой–средний.

## Рекомендуемый план

1. **Форкнуть tower-site в `noesis_adv`**, снять недвижимость-специфику
   (калькулятор рассрочки, планировки, поле «комнатность»), переименовать пакеты/бренд.
2. **Оставить ядро** нетронутым: auth, leads, funnels, contacts, analytics, files,
   news, site-build, деплой, CI — это фундамент, он готов.
3. **Ввести доменные сущности наружки**: `Surface` (взамен `Project`, + гео/формат/
   сторона/подсветка/GRP/цена-за-период), `Booking` (новая — бронирование по
   периодам), при необходимости `Deal`/`Contract`. Начать со схем в
   `packages/contracts` — это соответствует «контракты-первыми».
4. **Построить операционный слой инвентаря**: сетка занятости конструкция×период,
   проверка пересечений, статусы брони. Это новый, но изолированный модуль.
5. **Карта** (Яндекс.Карты) на публичном каталоге и в карточке конструкции CRM.
6. **Редизайн лендинга** под наружную рекламу поверх той же data-driven архитектуры
   и конвейера публикации.
7. **Поднять свой прод** (VPS/домен/секреты) по документации `docs/DEPLOYMENT_VPS.md`.

**Итог: брать tower-site за основу — обоснованно.** Он даёт готовый, качественный
CRM-каркас и конвейер «CRM → публичный сайт», совпадающий по контуру с задачей РА.
Основные вложения уйдут не в переделку, а в достройку доменного ядра наружной
рекламы — инвентарь, бронирование во времени и карту.
