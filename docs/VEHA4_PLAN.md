# Веха 4 — Публичный лендинг на данных из API (план)

Детальный план реализации Вехи 4 и согласованные продуктовые решения. Источник
объёма работ — [TASKS.md](../TASKS.md); этот документ раскрывает «как».

## Зачем

Документ фиксирует решения Вехи 4. Изначальная проблема: лендинг (`website/`,
Astro SSG) показывал **зашитые в `website/public/js/main.js` примеры**
(константы `PROJECTS`, `NEWS`, `DOC_CATEGORIES`), а не реальные данные из CRM.

Веха 4 переводит лендинг на реальные данные, **не меняя дизайн (1:1)**, с реальными
страницами ЖК/новостей, SEO и соответствием 152-ФЗ. На запуске база наполняется тем
же контентом, что зашит в статике, чтобы сайт выглядел идентично.

Контекст инфраструктуры: проект уже развёрнут на VPS по голому IP
`http://168.222.140.78` (ветка `claude/vps-deployment-ip-cetyy7`), база засеяна
этапами воронки и админом.

## Согласованные продуктовые решения

1. **Модель данных:** SSG — данные запекаются на сборке; после сохранения в CRM
   правки копятся как неопубликованные, затем админ запускает публикацию с
   дебаунсом ~1–2 мин (ради SEO; задержка приемлема).
2. **URL:** реальные страницы `/zhk/<slug>` и `/news/<slug>`; плавные наложения
   внутри сайта **остаются** (карточки получают `href`, JS перехватывает клик).
3. **Снятый/архивный ЖК:** старый URL → **301-редирект на каталог** (`/#catalog`).
4. **Пустые блоки** скрываются (вместе с пунктом меню); на запуске не пусто — сид 1:1.
5. **Сид 1:1:** 3 застройщика (Империя, Смарт-Строй, Иволга; привязка Ж→застройщик
   условная, правится в CRM); 8 ЖК; 6 новостей; 4 категории документов (без файлов).
   Фото скачиваются со старого облака в наше хранилище **сидом на VPS**.
6. **Цена:** хранится числом (`priceFrom`, ₽), на лендинге формат «от 3,7 млн ₽».
7. **152-ФЗ:** реальный текст Политики ПДн — [privacy-policy-source.md](./privacy-policy-source.md)
   (оператор ГСК «TOWER», почта gsktower@yandex.ru, домен в тексте `gsktower.com`).
8. **Сбой сборки:** наружу — только успешная сборка; при сбое сайт на последней
   рабочей версии, алерт в тот же Telegram, что и заявки.

## Фазировка

- **4.1 — Лендинг на реальных данных.** Сид + website на API + реальные страницы +
  ПДн/cookie + SEO. Пересборка пока **ручная** (`bun run deploy:vps`).
- **4.2 — Очередь публикации. ГОТОВО.** Бэкенд хранит неопубликованные правки,
  админ запускает публикацию с дебаунсом (~2 мин); сериализация (≤1 сборки);
  сайт на последней рабочей версии при сбое
  (атомарный релиз+симлинк); Telegram-алерт + сторожок простоя; индикатор статуса
  в CRM; сид стал «бутстрап-онли». Сборщик на хосте — systemd `gsk-site-builder`
  (детали и установка — в [DEPLOYMENT_VPS.md](./DEPLOYMENT_VPS.md)).
- **4.3 — Редактируемая «обвязка» из CRM + Яндекс.Метрика. ГОТОВО.** Singleton
  `SiteSettings` (JSON-переопределения поверх дефолтов в коде 1:1), admin-only,
  блокировка по версии; правка ставит флажок неопубликованных изменений (как контент в 4.2).
  Редактируемы: навигация, контакты/реквизиты, подписи кнопок/секций, второй
  контакт (WhatsApp/Telegram/звонок/ссылка вместо «Написать на почту»), число
  новостей (3/6), порядок и видимость ЖК на главной. Гайдрейлы: лимиты длины
  подписей + валидация ссылок. «Скрыть ЖК» убирает из каталога, блока «Документы»
  и бегущей строки, но `/zhk/<slug>` и sitemap остаются. Яндекс.Метрика: ID —
  настройка в CRM (пусто = выкл), анонимизация (без Вебвизора), цели
  `lead{source}` / `zhk_view` / `phone_click`; упоминание Метрики добавлено в
  `/privacy`. Детали — в разделе «Фаза 4.3» ниже.

### Шаг 2. Website на API (сборка)
- **Порядок деплоя:** website собирается на хосте и фетчит данные с backend — значит
  backend должен быть **поднят и засеян ДО сборки**. Переупорядочить `infra/deploy.sh`:
  (1) postgres+backend, миграции+сид; (2) сборка website/webapp; (3) поднять/релоуднуть
  nginx с новым `dist`. База фетча на билде — `http://127.0.0.1:3000` (опубликовать порт
  backend на localhost) или через nginx `/api`; env, напр. `BUILD_API_URL`.
- **`index.astro`:** во frontmatter зафетчить projects/news/documents; передать в
  `main.js` инжекцией JSON (`<script define:vars>window.GSK_DATA=…`), заменив хардкод;
  вёрстку оставить 1:1; скрывать пустые блоки и их пункты меню.
- **Реальные страницы** (`getStaticPaths` фетчит published): `src/pages/zhk/[slug].astro`
  (только `published && !comingSoon`; тот же markup, что наложение `projectPage`; SEO-meta),
  `src/pages/news/[slug].astro`, страница «Все акции и новости». Карточки получают `href`;
  `main.js` перехватывает клик → наложение. TRIUMPH («скоро») — без `href`.
- **Редирект снятых** на уровне `infra/nginx/default.conf`: для `/zhk/` и `/news/` —
  `error_page 404` → `return 301 /#catalog;`.

### Шаг 3. 152-ФЗ
- Статическая страница политики `src/pages/privacy.astro` (или ЧПУ) — текст из
  [privacy-policy-source.md](./privacy-policy-source.md).
- Ссылка на политику рядом с чекбоксом согласия во всех формах (hero в `index.astro`,
  модалки в `main.js`).
- Cookie-баннер — стандартный, в стиле лендинга, со ссылкой на политику; согласие в
  cookie/localStorage; не перекрывает контент.

### Шаг 4. SEO
- Уникальные `title`/`description` (для ЖК/новостей — из контента); ЧПУ по slug; Open
  Graph / Twitter Card; `canonical`; `sitemap.xml` + `robots.txt`
  (`@astrojs/sitemap` или вручную); Schema.org Organization.

## Подводные камни (учтены)
1. **Публикация без цены/комнатности:** сид пишет напрямую Prisma в обход
   `upsertProjectSchema`. Правка такого ЖК в CRM позже потребует заполнить поля.
2. **comingSoon (TRIUMPH):** в каталоге тизер «Скоро», `/zhk/` страницы нет (роут 404),
   карточка без `href`.
3. **Фото на чужом облаке:** зависимость только в момент сида; после — в нашем
   хранилище. Бакет должен быть жив при сиде. Дедуп по URL.
4. **Порядок деплоя:** website на API нельзя собрать до поднятия+сида backend.
5. **Формат цены** на лендинге — «от X,X млн ₽» из числа (нужен формат-хелпер).
6. **Редирект снятых страниц** — на уровне nginx (статика сама 404-ит).
7. **Домен в политике** — `gsktower.com`, хотя сайт пока на IP (так и оставляем).

## Фаза 4.3 — редактируемая «обвязка» + Яндекс.Метрика (реализовано)

### Согласованные продуктовые решения
1. Редактируемы все 4 «ручки»: видимость/порядок ЖК на главной; контакты и
   реквизиты; подписи кнопок/секций/навигации; число новостей.
2. Гайдрейлы обязательны: лимиты длины подписей (под макет 1:1) + валидация ссылок
   (только `http(s)`). Пустое поле = стандартное значение (дефолт из кода).
3. «Скрыть ЖК с главной» = убрать из каталога, блока «Документы» и бегущей строки;
   страница `/zhk/<slug>` и sitemap остаются (это НЕ «снять с публикации»).
4. Второй контакт — перенастройка существующей кнопки «Написать на почту» (тип
   `email | whatsapp | telegram | phone | link`, по умолчанию email = 1:1); нового
   элемента в дизайне нет.
5. Часы работы — два отдельных поля (будни/суббота); Политика ПДн остаётся
   статической (в редактор не выносится), в её текст добавлено упоминание Метрики.
6. Яндекс.Метрика: ID — настройка в CRM (пусто = не грузим), грузим всегда,
   анонимизация (без Вебвизора); цель `lead` с источником, плюс `zhk_view` и
   `phone_click`. Cookie-баннер информирующий — не трогаем.
7. Настройки — вход публикации: правка ставит флажок неопубликованного контента
   (`markContentChanged`), как контент в 4.2. Модель — singleton, admin-only,
   блокировка по версии.

### Устройство
- **Контракт** `packages/contracts/src/site-settings.ts`: схема переопределений
  (все поля опциональны), `SITE_SETTINGS_DEFAULTS` (тексты сайта 1:1),
  `SITE_SETTINGS_LIMITS`; хелперы `resolveSiteSettings` (дефолты+переопределения),
  `formatPhoneRu`/`phoneHref`, `deriveSecondaryContact`, `orderHomepageProjects`.
  Препроцесс схемы выкидывает пустые строки (очистка = возврат к дефолту).
- **Бэкенд** `backend/src/site-settings/`: модель `SiteSettings` (singleton, JSON
  `data`), сервис (resolve/raw/update + блокировка по `expectedUpdatedAt` → 409),
  роуты `GET/PUT /api/site-settings` (admin) и `GET /api/public/site-settings`
  (для сборки). Префикс добавлен в `backend/src/http/rebuild.ts`.
- **Лендинг**: `fetchSiteSettings` (фолбэк на дефолты — обвязка не роняет билд) +
  `buildChrome` (`website/src/lib/chrome.ts`); `index.astro` и под-страницы на
  настройках; Метрика — сниппет в `SiteHead.astro` (+ глобальный `window.ymGoal` и
  делегированный клик по телефону); цели в `main.js` (`lead`, `zhk_view`) и на
  странице ЖК (`zhk_view`).
- **CRM** `webapp/src/site-settings/SiteSettingsView.tsx`: вкладка «Сайт» (admin)
  со счётчиками длины, выбором второго контакта, перестановкой/скрытием ЖК.

### Verification (Фаза 4.3)
1. `bun run typecheck` (4 workspace) и `bun run test` (contracts + backend) — зелёные.
2. `GET /api/public/site-settings` на пустой базе = дефолты (сайт 1:1).
3. Сборка на дефолтах: обвязка как раньше, Метрика не грузится (ID пуст).
4. Переопределение (подпись навигации, ID Метрики, скрытие ЖК): подпись меняется,

5. Правка настроек в CRM → флажок неопубликованных изменений; после нажатия

6. Деплой: `git pull`, `bun run deploy:vps` (применит миграции).
