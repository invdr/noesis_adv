# Хранение файлов — продуктовые решения и техническое устройство

Этап «Хранение файлов» из [Вехи 3](../TASKS.md) — фундамент для фото ЖК, обложек
новостей и документов. Ниже зафиксированы продуктовые решения (как этим
пользуется контент-менеджер) и вытекающее из них техническое устройство.

## Зафиксированные решения

| # | Развилка | Решение |
| - | -------- | ------- |
| 1 | Когда файл уходит на сервер | **По «Сохранить»**, не при выборе. Пока менеджер не сохранил карточку — файлы живут только в браузере. Ноль файлов-сирот от брошенного создания. |
| 2 | Реакция на негодный файл | **Не дать дойти до ошибки**: браузер сразу подсвечивает файл не того типа/размера и не даёт сохранить; сервер — финальный строгий контроль по содержимому (magic bytes). |
| 3 | Когда делается ресайз/WebP | **Синхронно на «Сохранить»**, под честным спиннером. Сохранилось — значит все размеры готовы. Без фоновой очереди и состояния «фото обрабатывается». |
| 4 | Файл убрали из карточки | **Удаляется с диска сразу и навсегда** (со всеми производными). Сбойные сироты подчищаются в той же операции. Корзины нет. |
| 5 | Убрали весь ЖК/новость | **«Удаление» = архивация** (как у этапов воронки): запись и файлы остаются ради истории заявок и аналитики. Физически файлы стираются только при настоящем удалении записи из БД. |
| 6 | Доступ к файлам | **Публично через nginx** по обезличенной ссылке; ссылка живёт, пока существует файл. Снятие ЖК с публикации прячет его с сайта, но ранее розданные прямые ссылки продолжают работать (контент по своей природе публичный; проектные декларации публичны и юридически). |
| 7 | Размеры картинок | **3 версии** под `srcset`: ≈320 / 800 / 1600 px в WebP, плюс хранится оригинал. Без апскейла: если оригинал уже, лишние размеры не плодим. |

## Следствие решения №1 для архитектуры

Раз файлы уезжают только по «Сохранить», то загрузка — **не отдельный шаг «залил
→ получил ссылку → потом приклеил»**, а часть сохранения сущности. На практике:
сохранение ЖК/новости/документа — один многослойный (multipart) запрос с данными
и новыми файлами; обработка файлов выполняется **внутри** этого сохранения, в
одной транзакции. Если запись в БД не удалась — только что записанные на диск
файлы удаляются (никаких сирот).

Поэтому в этом этапе мы строим **переиспользуемый сервис файлов** (валидация,
обработка изображений, запись на диск, метаданные, генерация ссылок), а не
самостоятельный публичный эндпоинт «плавающей» загрузки. Сервис вызывают
эндпоинты ЖК/новостей/документов из следующих задач Вехи 3. Тонкий
`POST /api/files` есть как низкоуровневая точка (для прямого использования и
тестов), но продуктовый поток — загрузка вместе с сохранением карточки. Прямое
необратимое `DELETE /api/files/:id` — только для `admin`: это обходная
destructive-точка мимо прав на сущность; рядовое удаление файла из карточки
идёт через сервис сущности (он зовёт `deleteAsset`), а не через этот роут.

## Техническое устройство

- **Контракты** (`packages/contracts/src/file.ts`) — единый источник правил:
  допустимые типы (изображения `jpeg`/`png`/`webp`; документы `pdf` + OOXML
  `docx`/`xlsx`/`pptx`), лимиты (изображения ≤10 МБ, документы ≤25 МБ), целевые
  ширины производных, DTO `Asset` (с `renditions` для картинок: `variants` +
  готовая строка `srcset` + `thumbnailUrl`).
- **Модель** `Asset` (Prisma): `kind`, `originalName`, `mimeType`, `size`,
  обезличенный `storageKey`, `renditions` (JSON `{ width, key }[]`), автор
  загрузки. Бинарь — на диске, в БД только метаданные.
- **Сервис** (`backend/src/files/`): `validateUpload` (тип по magic bytes +
  размер — чистая функция), `storeUpload` (валидация → запись оригинала →
  WebP-производные через `sharp` → запись метаданных; при сбое чистит диск),
  `deleteAsset` (удаляет запись и все файлы). DTO строит публичные URL из
  `storageKey` и базового пути.
- **Хранилище**: каталог из `FILES_DIR` (env) на постоянном томе VPS, вне git;
  имена обезличены и разложены по подпапкам (первые символы ключа). Публичный
  префикс — `FILES_PUBLIC_BASE` (по умолчанию `/files`).
- **Инфра**: nginx раздаёт `FILES_DIR` как `/files/`; том переживает пересборку
  контейнеров; backend и nginx монтируют один том.

## Границы гарантии «ноль сирот»

Решения №1/№4 обещают, что брошенное создание и удаление файла не оставляют
мусора. Это держится так: файл уезжает на сервер только по «Сохранить»; запись
ведётся флагом `wx` (не перезатираем чужой файл при маловероятной коллизии имени);
при сбое внутри `storeUpload` (валидация, обработка, запись в БД) уже записанные
на диск файлы подчищаются, а реальные сбои удаления — логируются, а не глотаются
молча.

Остаётся один неустранимый на этом уровне зазор: падение процесса **строго между**
записью файла на диск и коммитом строки в БД (например, OOM или рестарт
контейнера в этот момент) может оставить файл без записи. Лимит размера тела до
буферизации в память снижает риск OOM, но не убирает его полностью. Закрывается
это периодической сверкой «диск ↔ БД» (фоновая чистка ключей без строки) — это
зафиксированный follow-up, не входящий в фундамент.

## Текущий статус

Файловый сервис используется для фото ЖК, новостей, документов, хода
строительства и публичной раздачи через nginx. Клиентские формы валидируют
тип/размер до отправки, сервер остаётся финальной точкой строгой проверки.
