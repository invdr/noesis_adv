## Решённые развилки

### ✅ 1. Единица брони — плавающий месяц
- Минимум 1 месяц; старт — **любой день** (напр. `05.05–05.06`, `21.07–21.08`).
- Срок **кратен месяцу** (целые месяцы, без дробей). Цена = цена/мес × число месяцев.
- Хранение — интервал дат `[начало, конец)` (полуоткрытый, стык встык не пересекается).
- Стык «31-х чисел»: `31.01 + 1 мес → 28.02` (клампим к концу месяца).
- ⚠️ Следствие: сетка занятости = **таймлайн/Гант** (полосы), а не таблица месяц-в-месяц.

### ✅ 2. Стороны конструкции — отдельные продаваемые поверхности
- Конструкция может быть **одно-, двух- или трёхсторонней**: `A`, `A/B`,
  `A/B/C` (куб).
- Стороны продаются раздельно и могут иметь свои параметры: направление/описание,
  цена, трафик/GRP, фото. Отдельное публичное название стороны пока не нужно:
  достаточно кода `A/B/C` + описания.
- Цена конструкции остаётся дефолтом для стороны. Если у стороны есть своя цена —
  используем её; если нет — цену конструкции; если нет обеих — «Цена по запросу».
- Целевая модель: отдельная сущность стороны конструкции, а не только
  `sideCount + side`. Бронь должна занимать конкретную сторону.
- У односторонней конструкции в UX выбор стороны не показываем, но технически это
  сторона `A`.
- Нельзя уменьшить число сторон, если на удаляемой стороне есть любые брони:
  `3 → 2` запрещён при бронях на `C`, `2 → 1` — при бронях на `B`.

### ✅ 3. Жизненный цикл брони
- Статусы: **Забронировано → В эфире → Завершено** + **Отменена**. Всё **вручную**.
  «В эфире» = плакат физически смонтирован; «Завершено» = по факту демонтажа.
- Отдельного «Подтверждено» **нет**. Мягкой брони/опции с TTL **нет**.
- **Занятость считается по датам** `[начало, конец)`: любая не-отменённая бронь
  занимает сторону. «Завершено» — операционная отметка, занятость не меняет;
  «Отменена» — убирает из занятости.
- ➕ **Новое требование:** напоминание менеджеру, что у брони **подходит срок**
  (веб-интерфейс + Telegram). Переиспользуем «следующий контакт» + «Мой день» +
  TG-уведомления. Параметры (за сколько дней, кому) — в развилке 6.

### ✅ 4. Кого/что бронируем
- **Тип брони** `kind: commercial | service`:
  - `commercial` — обязателен клиент-`Contact` (плательщик);
  - `service` — без клиента, обязательна **причина** из справочника (ремонт / своя
    реклама / резерв / демонтаж). Занимает (сторона+период) как обычная бронь; в
    аналитику **выручки** не входит, в **загрузку** — входит.
- **«Что размещаем»** — справочник **брендов** (`brandId`) + опц. свободный текст
  кампании (`campaignNote`), отдельно от плательщика. Бренд с **инлайн-быстрым
  добавлением** (как контакты), чтобы не блокировать менеджера; на публичной сетке
  бренд/клиент **не** показываем.
- **Новые справочники** (раздел «Справочники» CRM, правит admin): причины
  служебных броней, бренды.
- Бронь — **самостоятельный объект**: создаётся напрямую из сетки; `leadId`/сделка —
  **необязательная** привязка. Обязательны `Construction + side + период + статус`
  (+ клиент для `commercial`). Переход в сделку — Этап 4.

### ✅ 5. Цена брони
- `Construction.pricePerMonth` остаётся **каталожной ценой по умолчанию** для
  быстрого расчёта формы. Сторона может переопределить цену; при создании брони
  стартовая цена берётся с выбранной стороны, иначе с конструкции.
- Бронь хранит **снимок цены**, независимый от будущих изменений конструкции:
  `basePricePerMonth` (скопированная цена/мес, nullable), `durationMonths`
  (целое число месяцев), `totalPrice` (финальная сумма, nullable) и опциональный
  `priceNote` (пояснение скидки/ручного расчёта).
- Дефолт при создании: `totalPrice = basePricePerMonth × durationMonths`, если у
  выбранной стороны/конструкции задана цена. Менеджер может вручную изменить
  итоговую сумму; отдельную модель скидок/коэффициентов пока не вводим — аудит
  виден как разница между базовым снимком и финальной суммой + комментарий.
- Если `Construction.pricePerMonth = null` («по запросу»), коммерческую бронь можно
  создать без цены (`basePricePerMonth = null`, `totalPrice = null`) и заполнить
  сумму позже. В аналитику выручки такие брони не входят до появления `totalPrice`;
  отдельно показываем счётчик броней без цены.
- Служебные брони (`service`) выручку не формируют: `totalPrice` для них не нужен,
  но в загрузку/занятость они входят как обычные.
- Изменение цены на конструкции после создания **не меняет** существующие брони.
  При переносе/правке периода пересчёт цены должен быть явным действием менеджера,
  а не неявным сайд-эффектом сохранения.

### ✅ 6. Время
- Бэкофилл прошлых размещений **разрешён**: брони можно создавать с датами в прошлом
  и сразу нужным ручным статусом (`booked`, `onAir`, `completed`, `cancelled`).
- Период хранится как даты без времени: `startDate`, `endDate` (`[start, end)`).
  UI вводит локальные календарные даты; backend валидирует длительность целыми
  месяцами через общий helper и не делает автопереходов по текущей дате.
- У брони есть ответственный `managerId` (по умолчанию — текущий пользователь) и
  напоминание `reminderAt`. Дефолт — за **7 дней** до `endDate`; менеджер может
  отключить напоминание (`null`) или поставить свою дату. В «Мой день» и Telegram
  попадает ответственный; если он не задан, fallback — создатель брони.
- Правка/перенос текущей брони разрешены для всех не удалённых записей, если новый
  период не пересекается с занятостью той же стороны. Статусы меняются вручную.
  Отмена (`cancelled`) снимает занятость; физического удаления брони в обычном UI нет.

### ✅ 7. Целостность
- Пересечения ловим **в сервисе**: транзакция `Serializable`, поиск конфликтов по
  конкретной стороне конструкции и периоду `[startDate, endDate)` среди всех
  не-отменённых броней.
- Postgres `EXCLUDE` пока **не используем**: Prisma не поддерживает его декларативно,
  а в проекте принято не писать SQL миграций руками без необходимости. При единственном
  инстансе VPS сервисная проверка + `Serializable` достаточны для MVP; если появятся
  конкурентные продажи/несколько инстансов, вернёмся к `EXCLUDE`.
- Архивация конструкции блокируется, если есть будущие/текущие не-отменённые брони
  (`endDate` позже сегодняшнего дня). Исторические завершённые брони не мешают
  архиву. Жёсткое удаление конструкции блокируется при любых бронях.

### ✅ 8. Сетка занятости
- MVP CRM — отдельный раздел **«Брони»**: таймлайн/Гант с окном по датам, фильтрами
  по статусу/типу/конструкции/поиску и формой создания/редактирования брони.
  Единица строки — продаваемая сторона конструкции (`A/B/C`). У односторонней
  конструкции в интерфейсе строка может называться просто конструкцией.
- Форма брони открывается из раздела «Брони» и создаёт самостоятельную бронь без
  обязательной заявки. `leadId` остаётся nullable для будущего перехода в сделку.
- Публичная видимость занятости на Этапе 2 — только технический агрегат
  «свободно/занято на выбранный период», без клиента/бренда/цены. Полноценный
  публичный каталог с картой — Этап 3/5.

### ✅ 9. Аналитика загрузки/выручки
- Выручка MVP — **плановая**: все не-отменённые коммерческие брони с `totalPrice`
  (`booked`, `onAir`, `completed`), служебные и отменённые не входят.
- Если бронь длиннее выбранного периода, выручку распределяем пропорционально
  дням пересечения с периодом. Брони без цены участвуют в загрузке, но не в
  выручке; считаем их отдельно.
- Загрузка считается точно по сторонам/дням; UX-статусы: свободна, частично
  занята, занята + процент загрузки.
- В интерфейсе даты занятости показываем включительно: внутренний период
  `01.08–01.09` отображается как `01.08–31.08`.
- Первый экран CRM-аналитики: период от/до, быстрые кнопки (текущий месяц,
  следующий месяц, 3 месяца, 6 месяцев), карточки загрузки/выручки/свободных
  сторон/броней без цены и таблица по сторонам, сгруппированная по конструкциям.
- Архивные конструкции/стороны скрыты по умолчанию, но попадают в аналитику,
  если в выбранном периоде по ним были брони.

### ✅ 10. Публичная занятость и заявки
- Публичная карта: один пин = одна конструкция; рядом/в панели раскрываются её
  стороны.
- Пользователь выбирает период, одну или несколько сторон, затем отправляет одну
  заявку со списком выбранных сторон и периодом.
- Занятые стороны можно выбирать, но они явно помечены предупреждением. В CRM
  сохраняется статус занятости выбранной стороны на момент заявки.
- Занятость на публичном сайте = любые не-отменённые брони, пересекающие
  выбранный период. Если пересечений несколько, показываем интервалы:
  `Занято: 01–05.08, 20–25.08`.
- Из публичной заявки автоматически не создаём брони; бронь создаёт менеджер
  после контакта.
- Экспорт аналитики в CSV/Excel не входит в первый проход.

## Как обновлять прод в новой сессии

Текущий прод на VPS — **не git checkout**: код был синхронизирован rsync-ом из
локального workspace в `/var/www/noesis_adv`, без `.git`, `node_modules`,
локальных env и build-артефактов. Секреты живут только на VPS в
`/var/www/noesis_adv/infra/no-docker.env` и не должны перетираться.

1. Локально в workspace:

   ```bash
   cd /Users/ibrahim/Documents/Codex/noesis_adv
   git status --short
   PATH="$HOME/.bun/bin:$PATH" bun run typecheck
   PATH="$HOME/.bun/bin:$PATH" bun run test
   ```

2. Синхронизировать код на VPS (пароль/ключ SSH — у пользователя; секретный env
   исключён и останется на сервере):

   ```bash
   rsync -az --delete \
     --exclude='.git/' \
     --exclude='node_modules/' \
     --exclude='**/node_modules/' \
     --exclude='website/dist/' \
     --exclude='website/web/' \
     --exclude='webapp/dist/' \
     --exclude='backend/src/generated/' \
     --exclude='.astro/' \
     --exclude='.vite/' \
     --exclude='coverage/' \
     --exclude='playwright-report/' \
     --exclude='test-results/' \
     --exclude='infra/no-docker.env' \
     --exclude='infra/.env' \
     --exclude='infra/.site-build.lock' \
     --exclude='*.tsbuildinfo' \
     ./ root@77.222.32.54:/var/www/noesis_adv/
   ```

3. На VPS запустить no-Docker deploy:

   ```bash
   ssh root@77.222.32.54
   cd /var/www/noesis_adv
   bash infra/deploy-no-docker.sh
   ```

## Технические ориентиры / инварианты
- Прод-БД уже есть на VPS. Новые изменения схемы делать обычной Prisma-миграцией;
  init-миграцию больше не схлопывать и не переписывать под прод.
- Единый инстанс на VPS; in-memory троттлинг; фоновых демонов нет (cron — только бэкапы).
  Авто-снятия/авто-переходы делаем «лениво» на чтении, не демоном.
- Занятость и права — в сервисе, не в БД (кроме, возможно, `EXCLUDE`-констрейнта, п.7).
- Гейт перед деплоем: `typecheck` + `test` по всему монорепо.
